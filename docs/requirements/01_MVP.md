# MVP 정의: ThinQ Pregnancy Life Mode

> 참고: 원본 기획서(`1차문서.pdf`)에는 MVP 단계 구분이 별도로 명시되어 있지 않습니다.
> 아래 스코프는 기획서가 제시한 **우선순위 근거(기회영역 분석 — Actor 1 Action 1·2가 가장 중요도 높은 underserved 영역)** 와
> **핵심 가치 제안 4가지**를 기준으로, 검증 가능한 최소 단위를 판단해 구성한 제안입니다. 실제 착수 전 팀 논의로 확정이 필요합니다.

---

## 1. MVP 목표

기획서가 검증하고자 하는 핵심 가설은 다음과 같습니다.

> 임신·출산 전환가구는 달라진 생활조건에 맞는 생활관리 방법을 판단하고 실행하는 데 어려움을 겪을 것이다.

이 가설을 최소 비용으로 검증하려면, **"주수+당일 컨디션 기반으로 하루 루틴을 자동 생성해주고, 실행 여부를 기록한다"** 는
핵심 루프 하나만 완성도 있게 만들고, 가사 가이드 가전 실행처럼 디바이스 제어 검증이 필요한 요소는 이후 단계로 미루는 것이 타당합니다. 단, 수면 가이드의 '수면 루틴 시작하기' 가전 실행(FUC-W-SLEEP-002)은 MVP에 포함합니다.
단, 홈카메라 기반 실시간 탭(F6-1/F17)은 화면 설계서의 하단 4탭(홈·실시간·챗봇·캘린더) 구조상 상시 노출되는 탭이므로 **Phase 1(MVP) 범위에 포함**합니다.

**MVP 핵심 질문**: 사용자가 매일 컨디션을 입력하고, AI가 생성한 루틴을 실제로 실행/기록하는가? (검색 대신 루틴을 받아들이는가?)

> **AI 엔진은 MVP의 최우선 의존 컴포넌트입니다.** 서비스의 모든 판단(루틴 생성, 메뉴 추천, 챗봇 재조정)은 AI 엔진이 수행하며,
> 아내/남편 앱은 이 판단 결과를 보여주고 사용자 입력을 AI 엔진에 전달하는 역할만 합니다. 따라서 MVP 착수 시 화면 개발보다
> **AI 엔진 연동(프롬프트 설계, 입력 데이터 구조, 응답 스키마, 실패 시 폴백)을 최우선으로 검증**해야 합니다.

## 2. MVP 범위

### 2.1 포함 (아내용)

| 기능 | 대응 FUC ID (`04_1_기능요구사항명세서`) | 근거 |
|---|---|---|
| F1. 임산부 프로필 설정 (6단계 입력 + 입력 확인 화면, 전역 프로필 버튼 포함) | FUC-W-PROFILE-001~007(최초 등록), FUC-W-PROFILE-008(수정), FUC-W-MENU-001, FUC-W-SETTING-001 | 개인화의 기반 데이터, 없으면 아무 기능도 동작 불가. 전역 프로필 버튼 메뉴의 '설정'에서는 글자 크기(작게/기본/크게)를 조절한다. **최초 등록은 6단계(출산예정일 → 생년월일·신장·체중 → 초산/경산 → 단태/쌍태 → 알레르기 → 주의 진단) 순차 입력 후 입력 확인 화면(W-PROFILE-007)으로 마무리**하며, 확인 화면에서 항목을 선택해 수정하면 나머지 단계를 다시 거치지 않고 확인 화면으로 바로 복귀한다. 따라서 **`mode = onboarding`(최초 등록)과 `mode = edit`(수정) 두 진입 모드를 분리해 구현하는 것까지가 MVP 범위**다 |
| F1-1. 남편 초대하기 (초대 발송, 나중에 건너뛰기) | FUC-W-INVITE-001 | 남편 앱 전체(F12~F17)가 계정 연동을 전제로 하므로 온보딩 단계에서 필수. PLM은 **1회성 초대 토큰 생성과 ThinQ 알림 발송 요청**까지만 담당하고, 실제 알림 전달은 ThinQ 플랫폼이 처리하므로 구현 비용이 낮다 |
| F1-1 재진입(전역 프로필 버튼의 '남편 초대' 메뉴) | FUC-W-INVITE-002 | '나중에' 건너뛴 사용자의 유일한 재초대 경로. 없으면 최초 온보딩에서 스킵한 사용자는 영구히 남편 앱을 못 씀 → 가족 공유 가치 제안(핵심가치 3번) 이탈로 직결되어 MVP 필수 |
| F2. 오늘의 컨디션 체크 | FUC-W-COND-001~004 | 핵심 가설 검증에 필수 입력. **같은 날 '저장하고 마치기'로 루틴을 확정한 뒤 컨디션을 다시 체크해 새 루틴을 시작하는 경로도 MVP에 포함**한다(신규 화면 없이 기존 컨디션 체크 화면을 재사용하므로 구현 비용이 낮고, 하루 여러 번 상태가 달라진다는 핵심 가설과 직결됨). **확정 전 수정도 MVP 범위**이며, 수정 시 루틴을 다시 생성하고 4종 가이드를 함께 갱신한 뒤 남편에게 루틴 변경 알림을 보낸다 |
| F3. 오늘의 예정 활동 선택 | FUC-W-TASK-001, FUC-W-TASK-002 | 가사 루틴 조정의 입력값, 구현 비용 낮음(카드 선택 UI). **선택뿐 아니라 루틴 생성 이후의 수정도 MVP 범위**이며, 수정 시 처리는 F2와 동일하다. **병렬 기능이 아니라 컨디션 체크 직후에 반드시 거치는 순차 단계**다 — `오늘의 컨디션 체크(W-COND-001) → 오늘의 집안일 선택(W-TASK-001) → AI 하루 루틴 생성 → 홈 복귀` 순서로 동작하며, 미선택 시에도 컨디션만으로 루틴 생성이 가능하지만 화면 자체는 건너뛰지 않는다 |
| F4. AI 하루 루틴 생성 (식사/가사/건강/수면 4개 가이드, 텍스트 기반) | FUC-W-HOME-001, FUC-W-CALLBACK-001 | 서비스의 핵심 가치 제안 1·2번(개인화, 검색 대신 루틴) 검증 대상 |
| F5. 식사 가이드 (추천 + 챗봇 재추천) | FUC-W-MEAL-001~005 | Actor1-Action1(입덧/식사)이 최우선 underserved 영역으로 지목됨 |
| F6-1. 실시간 탭 — 홈카메라 활동 감지 및 누적 알림 | FUC-B-MOTION-001 | **Phase 1로 상향.** 화면 설계서의 하단 4탭(홈·실시간·챗봇·캘린더) 구조상 '실시간' 탭이 상시 노출되므로 탭만 비워두거나 숨길 수 없다. 당일 감지 로그 조회·감지 ON/OFF 토글까지 포함하되, **감지 임계값·횟수·시간 기준 등 상세 수치는 확정 대상이 아니며 백엔드 감지 로직 개발 단계에서 정의**한다 |
| F7. 건강 가이드 (스트레칭/산책 추천, 완료 체크) | FUC-W-HEALTH-001, FUC-W-HEALTH-002 | Actor1-Action2(통증/자세) 커버. 전일 모션 데이터가 있으면 부위 우선순위 판단에 반영하고, 데이터가 없으면 컨디션 입력만으로 생성한다 |
| F8. 수면 가이드 (루틴 제안 + 환경 설정 바텀시트 + '수면 루틴 시작하기' 연결 가전 실행 및 실행 기록) | FUC-W-SLEEP-001, FUC-W-SLEEP-001-1, FUC-W-SLEEP-002, FUC-W-RECORD-001 | Actor1-Action5(수면) 커버. 수면 가이드에는 별도 완료 체크 UI가 없으며, 상단 '수면 루틴 시작하기' 버튼 클릭을 오늘 수면 루틴의 실행 트리거로 사용해 Daily 리포트에 반영한다("오늘의 수면 팁"의 체크 아이콘은 목록 표시일 뿐 완료 체크가 아님) |
| F6. 가사 가이드 & 가족 분담 (카드 전송까지) | FUC-W-HOUSE-001, FUC-W-HOUSE-003, FUC-W-HOUSE-003-1 | 핵심 가치 제안 3번(가족 협력) 및 남편 앱과의 연결고리, 구현비용 대비 체감가치 높음 |
| F9. AI 챗봇 (맞춤형 질의 + 식사 가이드 메뉴 재조정) | FUC-W-CHAT-001, FUC-W-CHAT-003, FUC-W-CHAT-004 | 핵심 가치 제안 4번(실시간 재조정) 검증에 필요한 최소 범위. **챗봇은 하나이며 진입 경로에 따라 시작만 다르다** — 하단 탭으로 진입하면 맞춤형 질의응답만, 식사 가이드의 AI 재조정으로 진입하면 끼니 카드를 들고 시작해 메뉴 재조정(FUC-W-MEAL-003)까지 제공한다. 전체 루틴 자유 대화형 조정은 Phase 2로 이연 |
| F10. 루틴 실행 및 완료 기록 (직접 행동 + 가전 실행(가사 가이드·수면 루틴) + 남편 요청) | FUC-W-RECORD-001, FUC-W-RECORD-002 | 실행률 측정은 MVP 핵심 지표 |
| F11. Daily 리포트 & 컨디션 캘린더 (가전 작동 이력 포함 — 가사 가이드 가전 + 수면 루틴 가전) | FUC-W-HOME-002, FUC-W-REPORT-001, FUC-W-REPORT-001-1, FUC-B-CAL-001 | 데이터 축적 자체가 락인 효과의 핵심, 리텐션 유도 요소. **같은 날짜에 생성된 여러 루틴은 하나의 Daily 리포트로 통합**되며(날짜 기준 리포트 1개), 홈캠 관련 내용은 수치가 아닌 주의사항 문구 수준으로만 표시한다 |

## 3. MVP 사용자 흐름

### 아내
```
(최초 1회) 프로필 등록 6단계 → 입력 확인 화면 → 완료하고 시작하기
          → 남편 초대하기(초대장 보내기 또는 나중에) → 홈(컨디션 체크 전)
프로필 수정(전역 버튼, edit 모드) → 수정 항목만 변경 → 입력 확인 화면 복귀

아침 컨디션 체크 → 오늘 예정 활동(집안일) 선택 → AI 루틴 생성
→ 남편에게 오전 리포트 자동 전송
→ 식사·가사·건강·수면 가이드 확인 → (필요 시) 남편에게 가사 요청 카드 전송
→ 각 루틴 완료 체크 → 오늘의 일정 마치기 → Daily 리포트 확인
→ 저장하고 마치기 → 해당 루틴 확정 + 남편에게 Daily 리포트 전송 → 캘린더에 저장

(같은 날 다시 시작하는 경우)
저장하고 마치기 → 루틴 확정 → 오늘의 컨디션 체크 재진행 → 새 루틴 생성
→ 같은 날짜의 Daily 리포트 1개에 통합
```

> 오전 리포트 전송 조건과 Daily 리포트 전송 조건은 서로 다르다.
> 오전 리포트는 **컨디션 체크 완료(루틴 생성)** 시점에, Daily 리포트는 **'저장하고 마치기'** 시점에 남편에게 전달된다.

### 남편
```
(최초 1회) ThinQ 앱에서 초대 알림 수신 → 알림 선택 → 계정 연동 → 캘린더(남편 홈)
오전 레포트 알림 확인 → 가사 요청 카드 확인 → 확인 → 수행 → 완료했어요
→ 캘린더에서 이력 확인 → (필요 시) 실시간 홈캠 신체 정보 보기로 당일 감지 로그 조회
```

## 4. MVP 성공 지표 (제안)

원문서는 최종 성과 지표(ThinQ 사용 지속, 데이터 축적, 가전 구매 확대 등)를 제시하지만 이는 장기 지표입니다.
MVP 단계에서는 아래와 같은 선행 지표로 가설 검증을 판단하는 것을 제안합니다.

| 지표 | 검증 대상 |
|---|---|
| 컨디션 체크 D7/D30 리텐션 | "매일 입력할 만큼 가치가 있는가" (핵심 루프 지속성) |
| AI 루틴 중 실제 완료 체크 비율 | "제안이 실행 가능한 수준으로 개인화되었는가" |
| 식사 가이드 챗봇 재추천 사용률 | "AI 재조정 가치 제안이 통하는가" |
| 가사 요청 카드 전송→완료 전환율 | "가족 분담 흐름이 실제로 작동하는가" |
| 남편 앱 오전 레포트 확인율 | "파트너 참여가 유지되는가" |

## 5. 리스크 (MVP 한정)

- **F6-1(실시간 탭)을 Phase 1에 포함하면서 생기는 리스크**: 홈카메라 하드웨어 의존성과 임계값 기반 행동 판단 로직이 MVP 일정 안으로 들어온다. 감지 기준값·횟수·시간 기준이 아직 확정되지 않았으므로, MVP에서는 **감지 로그 수집·조회와 ON/OFF 토글까지만 확정 범위**로 두고 수치 기준은 백엔드 감지 로직 개발 단계에서 정의한다. 또한 의료 진단으로 오인될 소지에 대한 UX/법무 검토가 개발과 병행되어야 한다
- 홈캠 데이터가 없거나 감지가 OFF인 사용자에게는 건강/수면 가이드가 컨디션 입력만으로 생성되므로, 두 경우의 가이드 품질 차이를 사용자가 납득할 수 있도록 근거 문구를 설계해야 함
- 가사 가이드 가전 실행이 빠진 상태(MVP의 가전 실행은 수면 루틴 한정)에서는 "정보 제공에서 끝나지 않는 실행 연결"이라는 핵심 가치 제안 3번이 부분적으로만 검증됨 → MVP 지표 해석 시 이 점을 감안해야 함
- **AI 엔진(외부 API/LLM) 의존 리스크**: 응답 지연·실패·비용이 서비스 전체 체감 품질을 좌우함 → MVP에서는 정교한 캐싱·재시도 로직 없이 최소 폴백(이전 루틴 재사용)만 확보하고, 고도화는 Phase 2로 이연
