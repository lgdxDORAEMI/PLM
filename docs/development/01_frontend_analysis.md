# 1. Product Understanding

## 서비스 목적

PLM(ThinQ Pregnancy Life Mode)은 임신 주차와 당일 컨디션을 바탕으로 식사, 가사, 건강, 수면 영역의 생활 가이드를 하나의 흐름으로 제공하고, 필요한 일을 배우자와 나눌 수 있도록 돕는 임신 생활 지원 서비스다. 사용자가 매일 여러 정보를 직접 검색하고 판단하는 부담을 줄이며, 그날의 상태를 실제 생활 행동과 가족 협업으로 연결하는 것이 목적이다.

## Target User

- **주 사용자:** 임신 중 신체 변화에 적응하면서 일상생활을 관리해야 하는 임산부. 대표 페르소나는 임신 28주차의 직장인 한서현(30세)이다.
- **보조 사용자:** 임산부의 상태를 확인하고 가사 요청을 수락·완료하며 일상 지원에 참여하는 배우자/파트너다.
- **외부 연계 주체:** AI 엔진, ThinQ 가전, 홈 카메라가 문서에 정의되어 있다. 단, 실제 가전 실행과 실시간 모션 기능은 MVP 이후 범위다.

## 사용자가 겪는 문제

- 임신 주차와 당일 상태에 따라 입덧, 소화, 통증, 자세, 체중·혈당, 수면 문제가 계속 달라진다.
- 식사·운동·가사·수면 정보를 매번 따로 검색하고 선택해야 해 판단 피로가 크다.
- 신체 부담 때문에 직접 수행하기 어려운 집안일이 생기지만 배우자에게 상태와 필요한 일을 전달하는 과정도 부담스럽다.
- 하루의 컨디션과 수행 내역이 흩어져 있어 변화와 생활 패턴을 연속적으로 파악하기 어렵다.

## 서비스가 제공해야 하는 핵심 가치

- **개인화:** 임신 주차, 프로필, 당일 컨디션과 계획을 반영한 생활 가이드 제공
- **통합성:** 식사·가사·건강·수면을 하나의 오늘 루틴으로 확인
- **행동 가능성:** 정보 제시에 그치지 않고 선택, 조정, 완료 기록, 배우자 요청으로 연결
- **가족 협업:** 배우자가 임산부의 상태와 요청을 확인하고 처리 상태를 공유
- **연속성:** 일별 기록과 캘린더를 통해 컨디션 및 수행 결과를 누적 확인
- **안전성과 신뢰:** 의료 진단처럼 표현하지 않고, 개인정보 동의와 접근성을 갖춘 차분하고 신뢰도 높은 경험 제공

# 2. Core User Journey

서비스 흐름도에 정의된 흐름을 기준으로 정리했다. MVP 이후 기능은 별도로 표시했다.

| Step | User Goal | User Action | Screen | Result |
|---|---|---|---|---|
| 1. 프로필 등록 | 개인화에 필요한 기본 정보를 입력한다 | 예정일과 신체·임신 관련 정보를 입력하고 저장한다 | W-PROFILE-001 프로필 | 임신 주차 및 개인화 가이드 생성에 사용할 프로필이 저장된다 |
| 2. 배우자 초대 선택 | 배우자와 서비스를 연결한다 | 초대 링크를 발급·공유하거나 나중에 하기를 선택한다 | W-INVITE-001 배우자 초대 | 초대 링크가 공유되거나, 추후 메뉴에서 다시 진입할 수 있다 |
| 3. 초대 수락 | 임산부 계정과 파트너 계정을 연결한다 | 초대 링크를 열고 설치·로그인 후 초대를 수락한다 | H-INVITE-001 초대 수락 | 링크가 유효하면 두 사용자가 연결되며, 오류 시 연결 실패 상태가 표시된다 |
| 4. 오늘 상태 확인 | 오늘 필요한 안내를 시작한다 | 홈의 환영 카드에서 임신 주차와 주차별 팁을 확인한다 | W-ROUTINE-001 통합 홈 | 컨디션 미입력 시 입력 CTA가 표시되고, 입력 완료 시 오늘 가이드가 표시된다 |
| 5. 컨디션 입력 | 오늘 몸 상태를 기록한다 | 컨디션 항목을 선택·입력하고 저장한다 | W-COND-001 컨디션 입력 | 오늘 상태가 저장되고 예정 활동 입력 단계로 이동한다 |
| 6. 예정 활동 입력 | 오늘 일정에 맞는 루틴을 준비한다 | 예정 활동을 선택·입력한다 | W-ACT-001 예정 활동 | 컨디션과 활동 정보가 오늘 가이드 생성 입력으로 전달된다 |
| 7. 오늘 루틴 생성 | 한 화면에서 오늘의 생활 가이드를 받는다 | 생성 진행 상태를 기다린다 | W-ROUTINE-001 통합 홈 | 정상 시 개인화된 4개 가이드, 실패 시 대체 가이드가 표시된다 |
| 8. 식사 선택 | 오늘 상태에 맞는 식사를 결정한다 | 추천 식단을 확인하고 수락하거나 대화로 재추천을 요청한다 | W-MEAL-001 식사 가이드, W-CHAT-001 채팅 | 식사가 확정되고 기록·공유 가능한 상태가 된다 |
| 9. 가사 분담 | 신체 부담이 큰 일을 배우자에게 요청한다 | 가사 카테고리와 항목을 선택해 요청한다 | W-HOUSE-001 가사 가이드 | 연결된 파트너에게 가사 요청이 공유된다 |
| 10. 가사 요청 처리 | 배우자가 요청을 확인하고 수행한다 | 요청을 확인하고 수락한 뒤 완료 처리한다 | H-REQUEST-001 가사 요청 | 요청 상태가 요청됨 → 확인함 → 완료로 갱신되고 임산부 및 리포트에 반영된다 |
| 11. 건강 가이드 수행 | 컨디션에 적합한 건강 행동을 수행한다 | 건강 가이드를 확인하고 수행 완료를 기록한다 | W-HEALTH-001 건강 가이드 | 건강 행동의 수행 결과가 오늘 기록에 반영된다 |
| 12. 수면 준비 | 오늘 상태에 맞는 수면 환경을 준비한다 | 수면 환경 카드를 선택하고 값을 조정한 뒤 시작한다 | W-SLEEP-001 수면 가이드 | MVP에서는 추천·설정 경험과 기록을 제공하며 실제 가전 실행은 이후 연계 대상이다 |
| 13. 하루 기록 확인 | 오늘의 상태와 수행 결과를 돌아본다 | 완료 내역과 일일 리포트를 확인한다 | W-REPORT-001 일일 리포트 | 컨디션 및 가이드 수행 결과가 요약된다 |
| 14. 누적 변화 확인 | 날짜별 컨디션과 기록을 확인한다 | 캘린더에서 날짜를 선택한다 | W-CAL-001 컨디션 캘린더 | 선택 날짜의 기록과 리포트로 이동하거나 요약을 확인한다 |
| 15. 배우자 상태 확인 | 배우자가 임산부의 오늘 상태를 파악한다 | 아침 리포트 알림 또는 캘린더를 연다 | H-REPORT-001 아침 리포트, H-CAL-001 파트너 캘린더, H-NOTI-001 알림 | 연결된 임산부의 상태와 필요한 지원 정보를 읽기 전용으로 확인한다 |
| 16. 실시간 자세 확인 (Phase 2) | 카메라 기반 자세 상태를 확인한다 | 실시간 탭에서 측정을 시작한다 | W-MOTION-001 실시간 모션 | 모션 분석 결과를 확인한다. MVP Frontend 구현 범위에서는 제외된다 |

# 6. Design Requirement

## Visual Direction

- ThinQ 생태계와 어울리는 차분함, 돌봄, 집, 신뢰, 부드러운 기술의 인상을 유지한다.
- 유아용·캐릭터 중심·캔디 컬러·AI 대시보드 같은 표현을 피한다.
- Glassmorphism, Neumorphism, 과도한 그라디언트·장식·반복 애니메이션을 사용하지 않는다.
- 카드 남용, 동일한 형태의 반복, 무분별한 파스텔 배경을 피하고 정보 위계를 우선한다.

## Color

- Canvas `#F8F7F5`, Surface `#FFFFFF`, Subtle Surface `#F5F3F1`
- Primary Text `#1F1F1F`, Secondary Text `#65615F`, Tertiary Text `#8A8582`
- Border `#E9E5E2`, Strong Border `#DDD8D5`, Focus/Disabled Border `#C9C3BF`
- Primary 600 `#C6426A`를 중심으로 정의된 Rose Scale을 사용한다.
- Semantic Color는 Success `#357861`, Warning `#9A6A17`, Danger `#B64048`, Info `#416C8A` 및 각각의 배경색을 사용한다.
- Category Color는 Meal `#5F846A`, Home `#A85B70`, Body `#5C7191`, Sleep `#7560A3` 및 각 tint를 사용한다.
- 의미 색상은 텍스트·아이콘·라벨을 함께 사용하며 색만으로 상태를 전달하지 않는다.

## Typography

- 글꼴 우선순위는 Pretendard → Noto Sans KR → 시스템 기본 글꼴이다.
- 주요 Scale은 Display `28/38/700`, Title 1 `24/34/700`, Title 2 `20/29/700`, Heading `18/27/700`, Body 1 `16/25`, Body 2 `14/22`, Label `13/19/600`, Caption `12/18`이다.
- 문구는 짧고 현재 상태와 다음 행동이 분명해야 하며, 의료적 진단처럼 단정하지 않는다.

## Spacing, Size, Radius, Elevation

- 4px 기반 간격 체계를 사용한다.
- 화면 좌우 여백은 Mobile 20px, Tablet 28px를 기준으로 한다.
- Desktop 콘텐츠 폭은 일반 화면 480~720px, Form 520~560px, Dashboard 최대 720px 범위로 제한한다.
- Radius는 xs 6, sm 10, md 14, lg 18, xl 24, pill 999를 사용한다. Input 12, Card 14~16, Hero 18~20, Modal 20~24, Button 14~16을 기준으로 한다.
- 기본 구분은 얇은 Border를 우선하며 Shadow는 제한적으로 사용하고 Hover 시 가벼운 Elevation 변화를 허용한다.

## Components

- 중앙화 대상: `AppColors`, `AppTypography`, `AppSpacing`, `AppRadius`, `AppTheme`
- 공통 구조: AppShell, TopAppBar, 역할별 Navigation
- 공통 입력·행동: Button, Input, SelectionCard
- 공통 정보 표현: InfoCard, HeroStatus, ProgressMetric, GuideTaskCard
- 대화·오버레이: ChatBubble, Modal
- Icon은 기본 20/24px Line Icon을 사용하며, Filled Icon은 선택·상태 표현에 제한한다. Emoji를 기능 아이콘으로 사용하지 않는다.

## Interaction and Motion

- Hover, Focus, Pressed, Selected, Disabled, Loading, Empty, Error, Skeleton 상태를 일관되게 정의한다.
- 짧은 상호작용은 160~220ms, 레이아웃 전환은 240~300ms 범위를 사용한다.
- Reduced Motion을 지원하며 지속적으로 반복되는 Pulse 효과를 피한다.

## Responsive and Accessibility

- Breakpoint는 0, 600, 1024, 1440px을 기준으로 한다.
- Mobile은 단일 Column과 하단 Navigation을 사용하고, Tablet은 주 콘텐츠 폭 560~680px, Desktop은 최대 720px 및 필요 시 보조 정보를 2 Column으로 구성한다.
- WCAG AA 기준을 목표로 일반 텍스트 대비 4.5:1, 큰 텍스트 3:1 이상을 지킨다.
- 터치 Target은 최소 44×44px을 확보한다.
- 키보드 탐색, 명확한 Focus, Semantics, Icon Tooltip, 200% 글자 확대를 지원해야 한다.

Backend Dependency:

## 프로필과 임신 주차

Backend Dependency:

- Future API: 프로필 조회·저장·수정 및 예정일 기반 주차 정보 제공
- 현재 Mock 필요: 신규/기존 프로필, 유효성 오류, 저장 성공·실패, 주차별 예시 데이터

Backend Dependency:

- 현재 Mock 필요: 생성 전·중·완료·실패, 저장된 가이드, 식사·가사·건강·수면 샘플

## 식사 추천과 대화 조정

- 현재 Mock 필요: 추천 목록, 미연결, 전송 중, 각 요청 상태와 실패 시나리오

다음 항목은 문서 간 충돌, 정의 부족 또는 구현 전 확인이 필요한 사항이다. 이번 분석에서 임의로 결정하지 않는다.
