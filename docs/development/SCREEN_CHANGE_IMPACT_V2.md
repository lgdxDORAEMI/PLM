# 화면 변경 영향도 V2

작성일: 2026-09-17  
범위: 신규 요구사항과 현재 **Flutter** 구현의 차이 분석. 구현 지시가 아닌 후속 수정의 기준 문서.

## 1. 판단 기준과 조사 범위

- 요구사항 근거는 `docs/requirements/renew/`의 6개 문서 전체, `docs/requirements/아내_화면설계서.pdf`(26쪽), `docs/requirements/남편_화면설계서.pdf`(8쪽), `docs/requirements/아내 화면 DB스키마.pdf`(6쪽), `docs/requirements/남편 화면 DB 스키마.pdf`(3쪽)로 한정했다. PDF는 페이지 이미지에서 버튼, 탭, 하단 메뉴, 팝업, 상태별 화면, 역할별 이동 경로도 확인했다.
- 구현 여부의 근거는 `frontend/lib`의 현재 코드만 사용했다. 코드에 있는 동작을 신규 요구사항으로 역추론하지 않았다. 기존 흐름도, `.mmd`, 기존 매핑·상태 문서, 과거 기획·화면설계서, README의 기능 설명은 판단 근거에서 제외했다.
- 화면 식별자는 `renew/04_1_기능요구사항명세서.md`의 **FUC ID ↔ 화면 ID 매핑**과 지정 PDF의 표기를 사용한다. `W-HEALTH-002`처럼 UI가 아직 그려지지 않은 항목도 매핑상의 ID로 적는다. 새 Screen ID를 만들지 않는다.
- 상태 판정: **유지**는 현재 화면의 구조를 재사용할 수 있다는 뜻, **수정**은 화면은 있으나 데이터·상태·이동·권한을 바꿔야 한다는 뜻, **신규**는 요구된 화면/오버레이가 Flutter 제품 경로에 없다는 뜻, **삭제 후보**는 신규 범위에 맞지 않는 현재 UI라는 뜻이다. `유지`도 백엔드 완료를 뜻하지 않는다.
- `renew`의 MVP/Phase 구분을 적용한다. Phase 2 기능은 신규 화면으로 임의 확장하지 않고 기존 진입점의 처리 여부만 기록한다.

## 3. 라우팅과 사용자 전환

1. **진입**: ThinQ 배너/메뉴(`B-ENTRY-001`) → 아내 미등록 `W-PROFILE-001`, 등록 완료 `W-HOME-001`; 남편은 ThinQ 초대 알림 수락 전에는 초대 필요 안내, 연동 후 `B-CAL-001`. 현재 `MockEntryService`는 기본적으로 `ProfileStore`만 보고 아내 상태를 결정한다. `AppRouter.resolveLaunchRoute`에는 역할 분기가 있으나 실제 ThinQ 세션과 연결되지 않았다.
2. **아내 최초 등록**: `W-PROFILE-001~007` → `W-INVITE-001` → 아내 홈. 현재 `ProfileSetupScreen._complete`는 곧바로 아내 홈으로 이동한다. 프로필 재진입(`mode=edit`)은 입력 확인/항목 수정 후 메뉴로 돌아오며 남편 초대를 다시 열지 않는다. 현재 모드 분리는 있지만 요약 편집을 취소해도 내부 draft 변경값이 남는 문제가 있다.
3. **매일 루틴**: 홈 CTA → 컨디션 → 집안일 선택 → 생성/폴백 → 동일 홈의 4가이드. 컨디션·예정 활동 수정은 **미확정 루틴**만 재생성하고 4가이드를 함께 갱신한 뒤 남편에게 루틴 변경 알림을 만든다. `저장하고 마치기` 이후 같은 날 재체크는 새 루틴이다. 현재 `TodayCareStore`는 단일 메모리 값이며 날짜/루틴 상태가 없다.
4. **리포트**: 홈의 `오늘의 일정 마치기`는 미확정 리포트 생성/표시만 한다. 리포트의 `저장하고 마치기`가 확정·캘린더 갱신·남편 Daily 리포트 전송을 한다. `남편에게 공유`는 확정 전 선택 동작이다. 현재 `MockRecordService.saveRecord/shareRecord`는 지연만 수행하며, `DailyReportScreen`은 저장 뒤 **캘린더**로 간다. 요구사항의 홈 초기화·남편 공유 상태를 실제 데이터로 처리해야 한다.
5. **남편 알림/요청**: 캘린더 벨 → 3종 알림 → 오전 리포트/요청 카드/변경된 날짜 요약. 요청 카드는 `미확인→확인→완료`이며 완료 전 확인 팝업 후 결과 화면으로 이어진다. 요청 상태 변화에 따른 아내 신규 알림은 없다. 현재 남편 알림 모델은 오전 리포트·요청 2종, 요청 화면은 카드 속 각 일마다 별도 버튼/상태를 쓴다.
6. **역할 전환**: 두 사람이 각자의 ThinQ 계정에서 이용하고, 아내가 초대하면 남편 계정이 연동된다. 앱 안에 임의의 아내↔남편 스위치를 추가할 근거는 없다. 남편은 아내 프로필 원본·컨디션 원본 입력값·AI 대화 이력에 접근하지 않고 공유 요약만 본다(`NFR-013`).

## 8. 삭제 후보와 유지 요소

- **삭제 후보**: 아내 초대 화면의 초대 링크 문자열·복사 버튼·설치/가입 안내·OS 링크 공유 문구; 남편 초대 수락 화면의 링크 기반 가입 단계(ThinQ 알림/토큰 경로로 교체).
- **삭제 후보**: 실시간 감지 카드의 `확인`/검토 상태, ‘자정에 초기화’ 문구, 남편 화면의 ON/OFF 조작, Phase 2 미리보기 문구. 로그 **데이터 삭제 기능**은 만들지 않는다.
- **삭제 후보**: Daily 리포트의 `관절 부담 초과 n회`/최다 관절 수치, 근거 없는 고정 수치. 홈캠 감지 내용은 주의사항 문구로만 표시한다.
- **유지 가능**: 아내 4탭 구성, 프로필 6단계 wizard/요약 UI, 집안일 카드, 식사 끼니 목록·상세, 가사 3분류, 수면 바텀시트, 역할을 받는 공통 캘린더, 남편 알림/요청 카드의 기본 레이아웃. 유지 가능은 저장·권한·라우팅 완료 판정이 아니다.
- **Phase 2로 보류**: 가전 자동 실행/수면 일괄 실행, 전체 루틴 자유 대화, 홈캠 수치형 리포트, 상세 설정. 현재 코드에 있는 비활성 버튼은 범위를 설명하되 MVP 실행으로 취급하지 않는다.

## 10. 구현 우선순위

| 단계 | 선행 작업과 완료 판단 |
|---|---|
| **P0-1 진입/프로필/초대** | 역할·로그인 상태 분기, 프로필 6단계/요약 수정 취소, 최초 저장→ThinQ 초대→역할별 홈, 토큰·연동 계약. 아내/남편 계정 사이 공유 범위 확인 |
| **P0-2 일일 루틴 핵심** | 날짜·routine ID·미확정/확정 모델, 컨디션→집안일→AI 4가이드, 실패 화면/폴백, 입력 수정과 같은 날 재시작 구분, 오전 리포트 생성/전송 |
| **P0-3 가족 요청·보고서** | 요청 카드 상태 단위 확정 후 전송→확인→완료, 아내·남편 공유 조회; Daily 리포트 날짜당 1개·미리보기/확정/선택 공유, 캘린더 반영 |
| **P1-1 화면·라우팅 정합성** | 아내 4탭 루트 history, 남편 캘린더/오늘 실시간/알림 3종, 챗봇 진입 context, 남편 Daily 리포트 열람 경로 |
| **P1-2 홈캠/가이드 데이터** | 오늘 로그 공유 조회·아내 수집 토글·남편 읽기 전용, 익일 AI 입력, 주의사항 문구, 식사/건강/수면 완료·변경 이력 연결 |
| **P2 이후** | 가전 자동 실행, 수면 일괄 실행, 전체 루틴 대화, 수치형 홈캠 리포트, 설정 상세. 미정 수치·권한·동의 정책이 정해진 뒤 착수 |

후속 구현 착수 전 §9의 **확인 필요** 항목을 해당 문서 소유자와 정리해야 한다. 특히 오전 리포트 시점/구성, 요청 카드 상태 단위, 남편 실시간 권한은 데이터 모델과 화면 동작을 동시에 좌우한다.
