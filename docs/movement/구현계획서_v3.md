# 임산부 부담 자세 모니터링 알림 기능 — 구현 문서

카메라로 임산부의 자세(허리 숙임, 장시간 서있기, 앉았다 일어서기)를 실시간으로 감지해, 부담이 될 수 있는 패턴을 "실시간 탭"과 "일일 리포트"로 안내하는 기능이다. 의료 진단이 아니라 **관찰된 자세 사실 기반의 참고 정보**로 정의하며, 판정 결과는 확정적 위험도(%)가 아니라 관찰 수치(반복 횟수·지속시간·각도)와 문헌 근거(NIOSH, Frankel 등)를 함께 제시하는 서술형으로만 노출한다.

### 판정 로직에 별도 학습 모델을 두지 않는 이유

MediaPipe Pose는 관절 좌표만 출력하며 "이 자세가 부담되는가"는 판단하지 않는다. 이 판정은 학습이 아니라 **규칙 기반(기하학 계산 + 개인 캘리브레이션 편차 + threshold table)**으로 직접 구현했다 — 임산부 자세 부담에 대한 정답 라벨이 달린 공개 데이터셋이 없고, NIOSH 등 문헌 기준에 따른 판정이 근거 제시·책임 범위 설정에 유리하기 때문이다. MediaPipe 자체는 실시간 성능·Windows 네이티브 지원·Apache 2.0 라이선스를 이유로 다른 후보(mmpose, YOLOv8-pose, OpenPose, aihub 관절추론모델)보다 우선 채택했다.

## 2. 판정 로직

### 2.1 개인 캘리브레이션

절대 각도가 아니라 **개인 기준선 대비 편차**로 판정한다. 최초 연결 시(또는 재캘리브레이션 시) 사용자가 편하게 서 있는 자세를 일정 프레임 측정해 몸통 굴곡각·무릎각 기준값을 저장하고, 이후 모든 판정은 이 기준선과의 편차로 계산한다.

### 2.2 자세 분류

무릎각이 기준선보다 40도(`sitting_knee_dev_min`) 이상 작아지면 `Sitting`, 몸통 굴곡각이 기준선보다 20도(`bending_trunk_dev_min`) 이상 벗어나면 `Bending`, 둘 다 아니면 `Standing`으로 분류한다(무릎 조건이 몸통 조건보다 우선). 좌우 관절 중 한쪽이 가려지면 보이는 쪽 가시성으로 가중평균해 판정하므로, 측면(옆모습) 자세에서도 판정이 가능하다.

**Bending 임계값 개인화(2026-09-22 추가)**: 위 20도는 세션 시작 시 한 번, 사용자 프로필에 임신 주수·임신 전 체중이 모두 있으면 더 낮은 값으로 대체된다(`rule_engine.compute_bending_threshold_deg`). 프로필이 없거나 조회에 실패하면(온보딩 미완료 등) 모션 인식 자체는 계속 진행하고 20도 fallback을 그대로 쓴다 — 개인화는 어디까지나 기본 판정 위에 얹는 best-effort 보조 기능이다. 산정 근거는 §2.4 참고.

### 2.3 부담 라벨 체계

```
Normal → Repeated Load → Prolonged Load → High-load Action
```

| 자세              | 조건                                                                                         | 라벨                                          |
| ----------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Bending           | 한 번의 숙임이 8초(`prolonged_after_sec`) 이상 지속                                        | Prolonged Load                                |
| Bending           | 8초 미만이지만 60초(`repeated_window_sec`) 창 안에 3회(`repeated_after_count`) 이상 반복 | Repeated Load                                 |
| Bending           | 위 조건 미충족                                                                               | Normal                                        |
| Standing          | 15초(`prolonged_after_sec`, standing_burden) 이상 지속                                     | Prolonged Load                                |
| Standing          | 위 조건 미충족                                                                               | Normal                                        |
| Sitting           | —                                                                                           | (라벨 없음, 일어서는 순간에만 아래 규칙 적용) |
| Sit-to-Stand 전환 | 1초(`min_sit_duration_sec`) 이상 앉아 있다가 일어서는 순간                                 | High-load Action                              |

임계값은 전부 `backend/app/services/movement/rules.yaml`에 외부화되어 있어 코드 수정 없이 튜닝 가능하다. 모든 값은 데모 시연용 축소값이며(예: Standing 15초는 실서비스 NIOSH 기준 3시간 대신 축소), 실서비스 전환 시 재산정이 필요하다.

### 2.4 판정에 쓰는 값들을 그렇게 정한 이유

판정 로직에서 쓰는 값은 성격이 다른 세 갈래로 나뉜다.

- **① 문헌 근거로 확정한 값**: 수치 자체가 인체공학 표준·연구에서 나왔다.
- **② 원칙은 문헌 근거, 숫자는 자체 튜닝**: "이런 기준으로 부담을 판단한다"는 접근 자체는 표준 방법론이지만, 임산부 특이적 문헌이 없어 정확한 초·횟수는 자체로 정했다(2026-09-18 결정으로 MVP는 데모값을 그대로 확정, §8 "임계값의 자의성" 참고).
- **③ 엔지니어링 파라미터**: 인체공학적 임계값이 아니라 카메라 트래킹 노이즈를 거르기 위한 신호처리 파라미터로, 애초에 문헌 근거의 대상이 아니다.

#### ① 문헌 근거로 확정한 값

| 값                                                  | 쓰이는 곳                              | 근거                                                                                                                                                                                                                        |
| --------------------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bending_trunk_dev_min` = 20°(fallback)          | §2.2 Bending 분류                     | ISO 11226(정적 작업자세 평가) "수용 가능" 범위의 상한. RULA(McAtamney & Corlett, 1993)·REBA(Hignett & McAtamney, 2000)도 몸통 굴곡 0–20°/20–60°/>60° 구간 경계로 동일하게 20°를 사용 — 세 문헌이 같은 경계값에 수렴 |
| `prolonged_after_sec`(standing) = 15초            | §2.3 Standing 부담 라벨 경계          | NIOSH 정적 기립 권고(3시간)의 데모용 축소값(§8)                                                                                                                                                                            |
| Sit-to-Stand → High-load Action 분류               | §2.3 Sit-to-Stand → High-load Action | "일어서는 동작"을 부담 이벤트로 다루는 판단은 Lou 등(2001) 연구 근거                                                                                                                                                        |
| `absolute_angle_deg` = 30°, 누적 1시간당 HR 1.36 | §2.5 누적 전방굴곡 위험 신호          | Frankel 등,*Occupational and Environmental Medicine* — 덴마크 전국 등록 코호트(§2.5에 상세)                                                                                                                             |

#### ② 원칙은 문헌 근거, 숫자는 자체 튜닝

| 값                                                              | 쓰이는 곳                    | 원칙 근거                                                                                                                 | 숫자 확정 방식                                                                                                 |
| --------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `sitting_knee_dev_min` = 40°                                 | §2.2 Sitting 분류           | REBA 다리 점수표 — 무릎 굴곡 30–60°/>60°를 부담 점수 구간 경계로 사용(40°는 이 구간 안에 위치)                       | 정확한 40°는 자체 선택. REBA는 절대각 기준이라 캘리브레이션 편차 기준인 본 시스템과 정의가 완전히 같지는 않음 |
| `prolonged_after_sec`(bending) = 8초                          | §2.3 Bending 부담 라벨 경계 | Rohmert 정적근수축 내구시간 곡선 — 정적 자세 지속시간이 길수록 근육 부담이 커진다는 원칙                                 | 정확한 8초는 데모용 자체값                                                                                     |
| `repeated_after_count` = 3회 / `repeated_window_sec` = 60초 | §2.3 Bending 부담 라벨 경계 | ISO 11228-3(저부하·고빈도 작업의 인체공학적 평가, OCRA 기반) — 분당 반복 횟수로 부담을 평가하는 접근 자체가 표준 방법론 | 정확한 3회/60초는 데모용 자체값                                                                                |

#### ③ 엔지니어링 파라미터 (근거 대상 아님)

| 값                             | 쓰이는 곳 | 성격                                                               |
| ------------------------------ | --------- | ------------------------------------------------------------------ |
| `min_state_duration` = 0.5초 | §2.2     | 관절 인식 노이즈로 인한 순간적 오분류를 거르는 신호처리 파라미터   |
| `grace_period_sec` = 1.0초   | §2.2     | 일시적 가림(추적 실패) 동안 직전 상태를 유지하는 신호처리 파라미터 |

두 값은 인체공학적 임계값이 아니라 카메라 트래킹의 신뢰도 문제를 다루는 값이라, 애초에 문헌 근거를 대야 할 대상이 아니다.

#### Bending 임계값 개인화 상수의 근거

§2.2에서 언급한 개인화는 위 표의 20° fallback을, 임신 주수·임신 전 체중이 있는 사용자에 한해 더 낮은 값으로 보정한다. 같은 각도로 숙여도 배 무게로 늘어난 상체 부하 때문에 임신 후반부일수록 허리 부담이 커진다는 전제다. 쓰는 숫자는 3개이며, 구조는 "일반 성인 기준(20°)을 임산부 실측 자료(주당 0.29kg)로 보정"하는 것이다.

| 상수                                                             | 의미                              | 출처                                                 | 대상      |
| ---------------------------------------------------------------- | --------------------------------- | ---------------------------------------------------- | --------- |
| 20°(ISO 11226)                                                  | 몸통을 이 이상 기울이면 부담 자세 | ISO 11226 "수용 가능" 범위 상한                      | 일반 성인 |
| `PRE_PREGNANCY_UPPER_BODY_MASS_FRACTION` = 0.58                | 체중 중 상체(머리·몸통·팔) 비율 | de Leva(1996) 여성 신체 분절 표                      | 일반 여성 |
| `EXCESS_ABDOMINAL_MASS_PER_WEEK_KG` = 0.29kg/주(13주부터 적용) | 임신 2~3분기에 몸통에 붙는 무게   | Jensen, Doucet & Treitz(1996), 임산부 15명 매달 측정 | 임산부    |

왜 이 정도로 단순해도 되는가:

- 임신 말기에 늘어난 허리·골반 부담 중 무게 증가분은 약 10%, 자세 변화분은 약 50%다(Paul, Sallé & Frings-Dresen, 1996). 자세 변화는 카메라가 이미 재고 있으므로 무게 보정은 작은 조정만으로 충분하다는 판단이다.
- 배가 앞으로 나온 정도까지 반영해 더 정밀하게 계산해도 20° 기준은 14~18°로 나와, 단순 계산 결과(16.5°)와 큰 차이가 없었다.
- Standing 임계값과 누적 전방굴곡 30° 기준은 원래 임산부 연구(NIOSH·Frankel)에서 나온 값이라 별도로 보정하지 않는다(보정하면 이중 적용).

**한계 — 이 값을 설명할 때 함께 언급할 것**:

- ISO 11226의 20°를 "그만큼의 허리 부담"으로 해석한 것은 팀의 가정이다.
- 0.29kg/주는 15명의 평균이라 개인차를 반영하지 못한다. 결과는 실제로 잰 부담이 아니라 "비슷한 부담이 걸리는 각도"다.
- 임신 전 체중 대비 기준이라, 원래 체중이 무거운 사람일수록 부담이 더 크다는 점은 반영하지 않았다.
- **출처 확인 상태**: de Leva(1996)는 원문 PDF 확인. Jensen 등(1996)·Paul 등(1996)은 초록만 확인(원문 미확인). ISO 11226은 원문 미확인, 기존 팀 정리 기준.

### 2.5 누적 전방굴곡 위험 신호 (보조 지표)

위 라벨 체계와 완전히 별도로 동작하는 지표다. 캘리브레이션과 무관한 **절대각 30도 이상** 전방굴곡을, 자세 전환·짧은 추적 끊김과 무관하게 끊김 없이 누적한다(Frankel 등 덴마크 코호트 연구 근거 — 하루 누적 전방굴곡 1시간 증가마다 유산 위험 HR 1.36, 상관관계 연구이며 인과관계 확정 아님). 이 값은 실시간 라벨에는 영향을 주지 않고, 세션 종료 시 임계값을 실제로 넘긴 경우에만 리포트용 이벤트 하나로 남아 일일 리포트의 "오늘 누적 시간" 문구로만 노출된다.

### 2.6 삼분기(주수) 코멘트

판정 임계값에는 반영하지 않고, 리포트 문구에 "이 시기엔 이런 동작이 문헌상 더 주의가 필요합니다" 형태의 교육적 코멘트로만 병렬 노출한다.

## 3. 시스템 아키텍처

```
[Flutter Web 브라우저]
  카메라 프레임 캡처(getUserMedia) → WebSocket으로 JPEG 전송
      ▼
[FastAPI 백엔드]
  MediaPipe Pose → landmark 추출 → 피처 계산(굴곡각/무릎각) → 캘리브레이션 편차 적용
  → 규칙 엔진 판정(자세 + 부담 라벨) → 세션 상태 갱신
      │
      ├─ 프레임 결과(landmark + 라벨) → WebSocket 응답 → 브라우저 실시간 오버레이
      ├─ 실시간 탭 조회(GET /live) → 그 시점까지 누적 상태 반환 (풀 방식, 푸시 알림 없음)
      │
      ▼
  위험 이벤트만 Supabase Postgres에 저장(posture_events)
      ▼
  일일 리포트 집계 + 문구 생성 (GET /report/daily)
```

카메라 프레임 처리는 브라우저가 아니라 백엔드에서 수행한다 — 기존 Python 판정 로직(MediaPipe·규칙 엔진)을 그대로 재사용하기 위함이며, 브라우저 클라이언트 사이드 추론(WASM)은 판정 로직 전체를 JS/Dart로 재구현해야 해서 채택하지 않았다.

**네트워크 경계**: 카메라 프레임은 브라우저→백엔드로 전송되며 어디에도 저장하지 않고 처리 즉시 버린다(영상 저장 기능 자체가 없음). 로컬 데모 환경에서는 프론트·백엔드가 같은 PC의 localhost로 통신해 영상이 PC 밖으로 나가지 않지만, 가정 내 카메라와 클라우드가 분리되는 실서비스 단계에서는 이 경계를 재검토해야 한다(§7 향후 확장 참고).

`tools/motion_demo/`는 이 파이프라인 중 카메라 입력만 로컬 웹캠으로 바꾼 독립 실행 도구로, 별도 가상환경에서 계속 유지한다.

## 4. 인증

- REST(`GET /live`, `/events`, `/report/daily`)는 `Authorization: Bearer <Supabase access token>`으로 인증한다(`get_current_user`).
- WebSocket(`/live/stream`)은 브라우저가 핸드셰이크에 커스텀 헤더를 못 보내므로 `?token=<access_token>` 쿼리 파라미터로 받아 동일한 방식으로 검증한다(`get_user_from_token`).
- Origin 검증: `CORSMiddleware`는 WebSocket에는 적용되지 않아서, `/live/stream`은 연결 수락 전 `Origin` 헤더를 별도로 확인한다(HTTP CORS와 같은 허용 규칙 재사용). 허용되지 않은 origin이거나 없으면 코드 1008로 닫는다.
- **알려진 제약**: 지금은 데모 전용 단일 세션 모델이라(`_current_session_id` 전역 변수), `GET /live`는 로그인만 확인하고 "그 세션이 로그인한 사용자 것인지"까지는 확인하지 않는다. 다중 사용자 서비스 전환 시 세션을 사용자별로 조회하도록 바꿔야 한다.

## 5. 데이터 저장

### 5.1 저장 위치

Supabase Postgres 한 곳에 저장한다(프로필 등 다른 기능과 같은 프로젝트). 별도 Firestore/NoSQL 분리는 검토했으나 채택하지 않았다 — 저장 정책상 이벤트 자체가 저빈도(§5.2)이고, 실시간 탭도 pull 방식이라 NoSQL의 실시간 리스닝 장점을 살릴 이유가 없기 때문이다.

### 5.2 저장 정책 — "위험한 순간만 저장"

DB에는 부담이 실제로 확인된 순간만 남기고, 정상(Normal) 상태는 저장하지 않는다. 라벨이 Repeated Load 이상으로 올라간 구간, 그리고 Sit-to-Stand 같은 순간 이벤트만 `posture_events`에 기록된다 — 이 테이블에 행이 있다는 것 자체가 "위험 순간이 감지됐다"는 뜻이며, 별도의 `is_dangerous` 플래그는 두지 않는다. 세션 종료 시 남기는 누적 전방굴곡 기록(§2.5)도 연구 임계값을 실제로 넘긴 경우에만 저장한다.

### 5.3 테이블

- **`posture_calibration_profiles`**: `user_id`, `baseline_trunk_flexion`, `baseline_knee_angle`, `frame_count`, `captured_at`. 재캘리브레이션마다 새 행을 추가하고, 가장 최근 행을 현재 기준선으로 쓴다.
- **`posture_events`**: `user_id`, `session_id`, `posture_type`, `burden_label`, `trigger_reason`, `started_at`/`ended_at`/`duration_sec`, `rep_count_in_window`, `cumulative_bend_sec`. `posture_type`/`burden_label`/`trigger_reason`은 Postgres enum이 아니라 `text` + `check` 제약으로 둔다(임계값·라벨 체계가 튜닝 중이라 값이 추가/변경될 수 있어서).
- 두 테이블 모두 RLS는 켜고 정책은 두지 않는다 — anon/authenticated 키의 직접 접근을 차단하고, FastAPI(service role key)만 접근한다.
- 마이그레이션: `supabase/migrations/20260916000000_create_movement_tables.sql`.
- 실시간 골격 landmark(`PostureFrameState`)와 실시간 탭 누적 상태(`LiveAccumulatedState`)는 DB에 저장하지 않는다 — 조회·오버레이 전용이다.

### 5.4 저장소 구현

`EventStore`/`CalibrationStore` Protocol 뒤에 두 구현체가 있다 — `SupabaseEventStore`/`SupabaseCalibrationStore`(실제 API가 사용)와 `InMemoryEventStore`/`LocalFileCalibrationStore`(테스트 전용). Supabase 구현체는 생성자에서 `Client`가 아니라 `SupabaseService`를 받아 실제 DB 연결을 첫 요청 시점까지 지연시킨다 — 그래야 `SUPABASE_*` 환경변수가 없어도 앱 기동 자체는 실패하지 않는다.

### 5.5 아직 미구현

- NFR-008(민감정보 컬럼 암호화), NFR-014(AI 엔진 전달 시 최소 데이터 제한)는 코드 주석으로만 남아 있고 구현되지 않았다.
- NFR-012는 2026-09-18에 구현: `motion_consents`(STEP 14)를 `/live/stream` 연결 시점에 검사해 동의 없음/수집 OFF면 4003으로 거부한다. 스트림 도중 철회는 클라이언트가 WS를 끊는 것으로 처리한다.

## 6. API

| Method | Path                              | 설명                                                                                   |
| ------ | --------------------------------- | -------------------------------------------------------------------------------------- |
| WS     | `/api/v1/movement/live/stream`  | 카메라 프레임 스트리밍. 연결 시 캘리브레이션(필요하면) → 실시간 판정.`?token=` 필요 |
| GET    | `/api/v1/movement/live`         | 실시간 탭 조회(풀 방식). 활성 세션 없으면 404                                          |
| GET    | `/api/v1/movement/events`       | 로그인한 사용자의 이벤트 로그 조회                                                     |
| GET    | `/api/v1/movement/report/daily` | 일일 리포트 조회(`?date=YYYY-MM-DD`, 기본값 오늘 UTC)                                |

프로토콜 상세, `/report/daily` 집계 방식은 `docs/api.md` 참고.

### `/report/daily` 응답 요약

- `aggregates`: `(posture_type, burden_label)` 조합별 횟수/지속시간. Repeated Load 이상만 문구 생성.
- `top_burdened_body_part`: 지속시간 합이 아니라 `count × 라벨 심각도`로 계산(Sit-to-Stand는 항상 순간 이벤트라 지속시간 합으로는 절대 1위가 될 수 없어서).
- `cumulative_forward_bend_sec`: §2.5 누적 전방굴곡 기록의 그날 합계.
- `bending_burden_event_count`: Bending의 Repeated Load/Prolonged Load + High-load Action(Sit-to-Stand) 포착 횟수를 합친 값. High-load Action은 무릎 동작이라 `posture_type`이 실제로는 Standing으로 기록되지만, 이 지표에는 `posture_type` 조건 없이 포함한다.

## 8. 알려진 제약사항

- **임산부 대상 검증 데이터 부재**: 정량적 정확도는 일반인 대상 자체 테스트로만 확인했다.
- **임산부 체형에서의 landmark 정확도 미검증**: MediaPipe는 임산부 체형 위주로 학습되지 않았다. 배가 나온 체형에서 골반·허리 landmark 정확도가 떨어질 가능성이 있어, 어깨·골반·무릎 등 크고 안정적으로 검출되는 관절 위주로 피처를 설계했다.
- **임계값의 자의성**: 일부 임계시간·반복횟수는 판단 원칙은 문헌에 근거하지만 정확한 초·횟수는 임산부 특이적 문헌이 없어 자체 설정했다. `rules.yaml`로 파라미터화해 조정 가능하게 했다(값별 근거와 분류는 §2.4 참고). **2026-09-18 결정: MVP는 현재 데모값을 그대로 확정해서 쓴다.** 실서비스 값(예: Standing NIOSH 3시간) 재산정은 Phase 2.
- **의료적 판단 금지**: 확률·진단형 출력("무릎 손상 위험 82%" 등)은 근거가 없으므로 사용하지 않는다. 삼분기 코멘트도 "의학적으로 검증된 위험도"가 아니라 "일반적으로 알려진 주의사항 안내"로만 노출한다.
- **다중 사용자 세션**: §4에 명시한 대로 단일 세션 전역 상태를 아직 쓴다(`/live`). `GET /events`·`/report/daily`는 2026-09-18부터 남편이 호출하면 `partner_links`로 연동된 아내 데이터를 돌려준다(`api/v1/partner_scope.py`).
- **프론트 mock 화면과의 통합 (2026-09-20 갱신)**: 실제 하단 네비게이션(`ProductMovementScreen`)은 `GET /movement/events`, `/report/daily` API에 실연결됐다(Mock 표시 제거 완료, `docs/frontend/API_INTEGRATION_STATUS.md` 참고). 다만 이 문서의 실제 카메라·WS·Supabase 연동 화면(`MovementScreen`)은 여전히 정식 네비게이션 어디에도 연결되어 있지 않다 — 카메라 판정 자체를 정식 화면으로 통합하는 작업은 아직 남아 있다.
- **수동 E2E 확인용 별도 진입점 (2026-09-20 갱신)**: `MovementScreen`이 정식 라우트에 없어서, 배선(카메라 → WS → 규칙 엔진 → Supabase 저장)을 확인할 별도 진입점 `frontend/lib/main_movement_debug.dart`을 유지한다(`flutter run -d chrome -t lib/main_movement_debug.dart`로 실행, `main.dart`/`app.dart`는 건드리지 않음). 예전에는 access token을 손으로 붙여넣었지만, 2026-09-18부터 `.env`의 `DEMO_EMAIL`/`DEMO_PASSWORD`로 자동 로그인해 현재 세션의 access token을 그때그때 읽는 방식으로 바뀌었다(`movement_debug_screen.dart`·`app.dart`의 `/movement-debug` 라우트·토큰 하드코딩은 모두 제거됨). 연결이 4003으로 끊기면 토큰이 아니라 모션 동의/수집이 OFF인 것이다.

## 9. 향후 확장 계획

- **동작 의도 기반 인식 고도화**: 지금은 기하학적 규칙만으로 판정해 겉보기 각도가 유사한 동작(바닥 물건 줍기 vs 신발끈 묶기, Lifting/Carrying 등)을 구분하지 못한다. 스켈레톤 시퀀스 기반 행동 분류 모델(예: RHM-HAR-SK + ST-GCN/LSTM) 추가로 확장 가능.
- **다중 카메라 지원**: 카메라 간 동일 인물 세션 유지, 이중 카운팅 방지 로직.
- **ThinQ 앱 연동**: 이벤트 스키마를 외부 앱에서 소비 가능하도록 확장.
- **야간 스케줄러**: 실제 취침 시간대 자동 리포트 발송.
- **임상 검증**: 임산부 실사용자 데이터 확보 시 판정 기준 재검증 및 전문가 검토.
- **누운 자세 모니터링**: 장시간 앙와위 주의(순환계 이슈)를 별도 카테고리로 추가 검토.
- **온디바이스 추론 복원**: 가정 카메라와 클라우드가 분리되는 실서비스 단계에서, 프라이버시를 위해 브라우저/기기 내 클라이언트 사이드 추론으로 전환하는 것을 재검토.
- **NFR 이행**: 암호화, 동의 철회, AI 전달 최소 데이터 제한(§5.5) 실제 구현.
